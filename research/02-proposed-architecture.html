Proposed system architecture

Pick a plan,
not a mode.

An orchestrator whose adaptivity emerges from the shape of the plan it writes — and escalates only when a verifier says a step failed.

runtime loop · 5 moves 3 plan primitives reveal, don't predict
00 · Thesis

One dial, three settings, no menu

The naive design offers three modes — single-pass plan, recursive replan, ReAct — and a router that picks one up front. That quietly reintroduces the exact failure the Conductor research warned about: a fixed menu of human-designed options, chosen by a guess, before any evidence exists. Predicting "is this task unpredictable enough to need ReAct" is itself the kind of judgment you can't make well without doing the work first.

So we don't choose a mode. The orchestrator writes a plan, and the plan's structure determines how adaptive each part is. Adaptivity becomes a property of plan shape, escalated by verifier signal during execution — not a setting chosen in advance.

◆ First principle

Two loops, kept apart. The runtime loop answers a request. The measurement loop runs offline, scoring per-model and per-subtask success so the runtime's assignment step is calibrated rather than guessed. The runtime is what serves; the measurement loop is what makes it good. Build them as different systems.

01 · The runtime loop

Five moves, and the last one isn't optional

A fan-out — split the prompt, hand out the pieces, collect answers — is the weak baseline (it's roughly Mixture-of-Agents, the thing the Conductor beat). The loop that works adds difficulty assessment at the front and verification/synthesis at the back, with controlled visibility between steps.

  • Assess difficulty

    Decide whether this even needs splitting. Easy requests get one good model in a single step.

    why · mandatory decomposition wastes calls on simple prompts

  • Decompose — maybe

    Break into subtasks only when the task warrants it. Decomposition is a tool, not a reflex.

    why · the Conductor learned to vary step count by difficulty on its own

  • Assign to a fitting model with a tailored prompt

    Per subtask, pick the worker the measurement loop says wins it, and prompt-engineer the instruction to its strength.

    why · tailored subtasks carried weight even with routing removed

  • Execute with controlled visibility

    Run steps in the planned order, each worker seeing only the upstream results it's wired to. This is the topology — planner → writer → verifier — not a flat parallel spray.

    why · the gain came from structure, not from agents working in isolation

  • Verify & synthesize

    Check the result and combine into one answer. The piece a fan-out leaves out — and the reason MoA degraded when it couldn't tell a correct answer from a confident wrong one.

    why · synthesis without verification is how good answers get out-voted
02 · The plan representation

Three primitives, and mode falls out for free

Keep the Conductor's three-list schema and widen the output language with three step primitives. A plan made only of normal steps is plan-and-execute. A plan where a risky step carries a replan flag is the recursive setting. A step that drops into a self-loop is ReAct — scoped to that one piece. The orchestrator never selects a mode; it selects a plan.

Normal step

flag: noneSubtask → worker. Run once.

Replan on fail

flag: replanFails its verifier → spawns a local sub-plan (ADaPT-style).

Scoped self-loop

flag: reactObserve → decide → repeat, bounded, on one step only.
# extended schema — the planner emits this in one shot
model_id    = [ 3, 0, 1 ]
subtasks    = [ "Plan an approach", "Implement it", "Verify against tests" ]
access_list = [ [], ["all"], ["all"] ]
flags       = [ none, replan, react ]   # ← the new dimension
budget      = { max_depth:2, max_react_steps:4, max_spend:"$0.40" }
◆ Why reveal, not predict

No up-front mode classifier. Escalation fires on a verifier failure during execution, not a guess beforehand — the same correction the Conductor's RL provided, applied at runtime. A closed math problem stays a flat DAG; a step hitting a live API earns a self-loop; everything in between self-selects from evidence.

03 · Load-bearing constraints

Two things that sink this if skipped

ConstraintWhy it's non-negotiable
Hard budgetsUnbounded adaptivity becomes infinite loops and runaway cost — every source flags it. The dial needs a ceiling: max recursion depth, max self-loop steps, max spend per request.
Verifiers as triggerEscalation only works if a step can be told it failed. No verifier → nothing to escalate on → back to guessing. The whole design rests on automatic graders.
⚠ Domain limit

This recipe lives on verifiable tasks — code execution, math equivalence, MCQ matching. If your domain has no ground-truth checker, the replan/escalation machinery has no signal, and you're into LLM-judge territory with its reward-hacking risk. Confirm you can verify before committing to this architecture.

04 · The measurement apparatus

The renewable asset

Everything calibrated depreciates as models update — so the durable thing isn't a trained orchestrator or a frozen best-model table, it's the harness that produces them. Offline, run each worker on a bank of verifiable problems, measure per-model and per-subtask success, and emit a calibration table. That table is what the assign step reads.

The payoff is optionality: once you have measured competence, you can either bake it into a trained conductor or hand it to a frontier model as context. The ablations say the second gets most of the way for free — so the measurement loop, not the model on top of it, is where the engineering investment compounds.

Re-run, don't trust. Schedule the measurement loop to re-score whenever a worker version changes. Calibration is perishable; treat it like a cache with an expiry, not a constant.
05 · Build path

Where to start, and what to defer

  1. Frontier model as planner

    Have an existing model emit the three lists (plus flags) against a fixed schema, run them through your own executor. Single-pass only. No training. This is ~90% of the value and swaps instantly as models improve.

    start here

  2. Add the measurement loop

    Stand up verifiers per domain and the offline scoring harness. Now the assign step is calibrated, not guessed — the single biggest quality lever.

  3. Add escalation primitives

    Introduce replan and react flags plus budgets, once the single-pass version is solid. Adaptivity exactly where verifiers report failure.

  4. Train a conductor — only if needed

    Worth it for cheap, low-latency planning (so you're not paying a frontier model to plan every request) or sub-task preferences too fine to prompt — e.g. learning to swap a small open model in purely as a format-checker. Reproducing the Conductor is modest: 2×H100, ~960 tasks, released code.

    defer
⚠ Hidden infra

Open-source workers must be served somewhere — that's more GPU than the orchestrator itself, via self-hosted vLLM or a hosted provider. And any training run's real cost is the worker-API bill during rollouts, not the two training GPUs. Budget for both before committing to Phase 04.
