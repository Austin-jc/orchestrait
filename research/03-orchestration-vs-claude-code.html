A decision brief

Orchestrate, or just
use Claude Code?

Build-your-own orchestration and Sakana Fugu both bet on a model-of-models. Claude Code's workflows bet on one well-integrated model. The right call hinges on two variables — not on which sounds more sophisticated.

00 · The frame

It isn't "smarter vs simpler"

Orchestration's headline result — a model-of-models beating a single frontier model — came almost entirely from heterogeneity: routing each task to whichever model is strongest at it, winning because none is strongest everywhere. Strip the diversity and you strip the engine. So the comparison with Claude Code's workflows isn't abstract; it turns on whether your situation keeps that engine running.

Two variables decide it. Pool diversity — do you have many models or one — governs whether routing has any value at all. Control needs — do you require deterministic verification, hard budgets, and owned eval data — governs whether the framework's other properties justify it even when routing doesn't. The matrix above is the whole brief in one picture; the sections below show the work.

01 · What survives a single model

Three pillars, only some load-bearing alone

"Orchestration" bundles three distinct things. When the pool collapses to one model, they don't fail equally — and knowing which survive tells you exactly what you'd still be buying.

  • dies

    Routing — "best model for this task"

    Zero value by construction with one model. The Conductor's fix-everything-to-one-model ablation saw task-specific gains collapse to roughly nothing where that model already dominated.

  • survives

    Decomposition

    Splitting a task into focused subtasks, each solved in clean context. Independent of pool diversity.

  • survives

    Tailored prompting

    A sharp, purpose-written instruction per subtask. The same ablation still edged past the raw model largely on this.

  • survives

    Verification topology

    A separate checking pass with controlled visibility before synthesis. Survives — and is the basis of any single-model edge.

⚠ The catch

Claude Code's workflows already do decomposition, subagents in fresh context, and orchestration. So with one model, the surviving pillars are mostly things Claude Code provides too. The honest residual you'd be adding is narrower than it first looks — and it's about how control is exercised, not whether tasks get split up.

03 · What only each can do

The non-overlapping edges

Orchestration framework only here

  • Route across providers — the moment you add a non-Claude model, routing value switches back on
  • Gate progress on a real verifier (code execution, math equivalence) rather than the model's own judgment
  • Enforce a hard spend/depth/time ceiling no step can escape
  • Accumulate verified pass/fail as an owned dataset — regression detection, "did the new model improve at X"
  • Survive single-vendor disruption by swapping the pool

Claude Code workflows only here

  • Native filesystem, editor, terminal, and tool access out of the box
  • A coding loop tuned by the people who built the model
  • Zero infrastructure — no worker serving, no gateway, no verifier sandbox to maintain
  • Immediate; nothing to design before you're productive
  • Subagents and context management handled for you
04 · The Opus-only verdict

When the pool is one model

Run the subtraction honestly. Routing value → zero. Decomposition and subagents → Claude Code already does them. What's left that's genuinely yours is the control character: verifier-gated progress instead of self-assessment, hard budgets, and owned calibration. Whether that's worth a framework depends entirely on whether you need those three as first-class properties.

◆ Honest verdict

With Opus-only and general coding, Claude Code's workflows will likely win or tie — it's integrated, tuned, and the framework's defining advantage (heterogeneous routing) is switched off. Don't build it for that case. Build it when you have verifiable non-coding tasks needing deterministic control, when hard budgets and owned eval data are operational requirements, or — the decisive one — when you intend to run a multi-model pool, at which point the whole premise re-activates.

Put plainly: with only Opus, this framework is a verification-and-budgeting harness wrapped around Opus. Build it only if verification-and-budgeting is the thing you actually need.

05 · Three postures

Buy, build, or use what's integrated

It helps to see the three options as different postures rather than competitors on one axis.

Buy

Sakana Fugu

Hosted, learned conductor over a multi-vendor pool behind one API. Sovereignty / export-risk pitch. Can't self-host; benchmarks are vendor-reported; routing is opaque.

for · multi-model power, no build
Build

Your framework

Frontier-planner orchestration you own end-to-end: your pool, your verifiers, your budgets, your calibration. Real setup cost; full control and provider-agnosticism.

for · control + breadth + ownership
Use

Claude Code workflows

Integrated, tuned, single-vendor. Near-zero setup, strong on coding, model-judged control. No routing, no owned eval.

for · Claude-only, integrated work

Fugu and your framework are the same bet at different build-cost points; Claude Code is a different bet entirely. The choice between the first two is buy-vs-build; the choice against Claude Code is the pool-diversity question above.

06 · Decision rule

If / then

  • If · one model + general codingUse Claude Code workflows. Routing is off and Claude Code already does the rest, integrated and tuned. Building loses.
  • If · one model + verifiable, governed pipelineBuild the framework as a verify + budget harness. Worth it when deterministic control, hard budgets, and audit/eval data are requirements — even single-model.
  • If · many models + lighter control needsOrchestrate for routing. A frontier-planner framework, or buy Fugu. Routing is the engine; verification matters less here.
  • If · many models + high control needsBuild the full orchestrator. Both pillars active — routing and verifier-gated control. The strongest case for the design in Doc 02.
◆ The one-line test

Will your pool ever hold more than one kind of model? If yes, build toward orchestration now — routing returns the day you add the second model. If it's one model forever and the work is coding, Claude Code already has you covered.
